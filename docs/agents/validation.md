# Проверки и ревью

Все команды выполняются из корня репозитория. Python — 3.12+, PHP — 8.2+ с расширениями из [SMTP-инструкции](../smtp-hosting.md). Для браузерного сценария нужны Node.js, Playwright и Chromium/Chrome. Сначала проверьте имеющиеся зависимости; не добавляйте локальные абсолютные пути в репозиторий.

## Минимальная проверка изменений сайта

```sh
python3 build.py
python3 verify.py
python3 scripts/prepare_marketing.py
node --check dist/app.js
node --check dist/analytics.js
git diff --check
git status --short
```

Ожидается: 23 страницы, 0 индексируемых страниц в сборке по умолчанию, пустой список ошибок. Для команд проверки задавайте тот же `OUTPUT_DIR`, `BASE_PATH`, `SITE_URL`, `FORM_PROVIDER`, `INDEXING_ENABLED` и `METRICA_ID`, что использовали при сборке. Учитывайте переменные, унаследованные от окружения.

При правках только документации достаточно проверить факты по исходникам, относительные ссылки, команды и diff. Не запускайте весь набор без причины.

## Когда расширять проверку

| Изменение | Дополнительная проверка |
|---|---|
| Шаблоны, маршруты, ресурсы, префиксы, сборщик | Сборка GitHub Pages с префиксом и обе структуры PHP-пакета. |
| Форма, аналитика, consent, предзаполнение | `node scripts/check_marketing.mjs`; сценарии успеха и ошибки, отказ/отзыв согласия. |
| PHP, вложения, SMTP, приватные пути | Синтаксис PHP, интеграционный тест, оба архива, проверка состава архивов. |
| Внешний вид, навигация | Браузер: 390, 781 и 1440 px; изменённая страница, состояния шапки/меню/формы, отсутствие горизонтальной прокрутки. |
| SEO | Основной домен с индексацией и GitHub-копия без неё; canonical, sitemap, исключённые страницы, OG. |
| Реклама | Экспорт и валидация материалов. Не импортировать и не запускать кампании без соответствующей задачи. |

### Сборка с префиксом

```sh
OUTPUT_DIR=release/qa-pages BASE_PATH=/ligus-msk SITE_URL=https://aleshaio.github.io/ligus-msk INDEXING_ENABLED=0 METRICA_ID='' python3 build.py
OUTPUT_DIR=release/qa-pages BASE_PATH=/ligus-msk SITE_URL=https://aleshaio.github.io/ligus-msk INDEXING_ENABLED=0 METRICA_ID='' python3 verify.py
```

Используйте новый каталог вывода или очищайте только собственный каталог тестового результата. При изменении маршрутов убедитесь, что удалённые страницы не остались в копируемой `dist/`.

### SMTP и архивы

```sh
find server -name '*.php' -print0 | xargs -0 -n 1 php -l
PHP_BIN=php python3 server/tests/integration.py
INDEXING_ENABLED=0 METRICA_ID='' python3 scripts/build_hosting.py
INDEXING_ENABLED=0 METRICA_ID='' python3 scripts/build_hosting.py --layout regru
INDEXING_ENABLED=1 METRICA_ID='' python3 scripts/build_hosting.py --layout regru
```

Тест использует временную папку, локальный PHP-сервер и локальный SMTP-приёмник; внешняя почта не нужна. Архивы не должны содержать настоящие `config.php`, `.env`, `runtime`, логи или резервные копии. Публичная часть SMTP-сборки не должна содержать FormSubmit/Яндекс Формы. Приватная часть должна лежать за пределами document root.

Для Playwright, установленного отдельно, можно передать `PLAYWRIGHT_MODULE`; для системного Chrome — `CHROME_BIN`. Браузерный тест сохраняет отчёт и изображения в `release/marketing-qa/`. Отчёт не заменяет просмотр значимых визуальных изменений.

## Ревью ветки перед слиянием

1. Зафиксировать исходный commit ветки и общую базу с актуальной `origin/main`. Посмотреть список коммитов, diff и новые/удалённые файлы, включая скрытые.
2. Прочитать новые инструкции, workflow и скрипты до запуска. Проверить публикации, сетевые вызовы, секреты, права токенов и сторонние зависимости. Не смешивать ревью с запуском рекламы или отправкой настоящих заявок.
3. Для оптимизации сравнить набор URL и итоговые HTML, ресурсы, режимы формы/SEO, доступность и размеры страниц с базовой сборкой. Изменение количества строк само по себе не улучшение.
4. Проверить, что перенос исходников отражён в генераторе, упаковщике, валидаторах, CI, путях лицензий и документации. В сборку не должны попадать агентные заметки и временные файлы.
5. Исправить обнаруженные ошибки, выполнить применимые проверки и просмотреть полный итоговый diff. Проверить повторную сборку: она не должна создавать неожиданные изменения.
6. Перед слиянием обновить сведения об удалённом `main`. При его изменении проверить результат интеграции. Не использовать force-push, чтобы обойти конфликт.
7. Слить проверенный commit, отправить результат и проверить соответствующий запуск CI. Сообщить отдельно о слиянии и публикации. Push в `main` запускает GitHub Pages, но не REG.RU.

Описание результата: конкретная проблема → исправление → доказательство проверки → оставшееся ограничение, если оно есть. Не писать «всё проверено», если не запускалась часть необходимых проверок.
