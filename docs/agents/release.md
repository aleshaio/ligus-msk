# Публикация и эксплуатационные границы

## Два назначения

- `main` в GitHub автоматически публикует **GitHub Pages** через `.github/workflows/pages.yml`. Там нет PHP и рабочей SMTP-конфигурации основного сайта.
- **REG.RU / ligus-msk.ru** обновляется отдельно. Push и зелёный Pages workflow не означают, что основной домен обновлён.
- Последние подтверждённые сведения, пути, резервные копии и незавершённые задачи хостинга — в [docs/deployment.md](../deployment.md). Перед размещением сверьте их с фактическим состоянием.

## Сборка основной версии

```sh
INDEXING_ENABLED=1 METRICA_ID='' python3 scripts/build_hosting.py --layout regru
```

Результат: `release/ligus-regru.zip`, публичные файлы в `release/ligus-regru/www/ligus-msk.ru/`, приватные — в `release/ligus-regru/private/contact/`. Индексация уже открыта в основной версии: нельзя случайно закрыть её сборкой с настройками предпросмотра.

Пустой `METRICA_ID` отражает текущий выключенный счётчик. Если владелец впоследствии подключит настоящий счётчик, обновите документированный режим и сохраняйте его при следующих сборках. Не используйте тестовый ID в публичном релизе.

## Порядок обновления REG.RU

1. Убедитесь, что публикация входит в поручение. Сначала завершите изменения и проверки, затем размещайте готовую сборку. Не просите повторного разрешения, если оно уже получено.
2. Сверьте локальную сборку и текущие файлы сервера. Сохраните заменяемые файлы в закрытой резервной папке **вне** document root. Зафиксируйте путь резервной копии, без секретов.
3. Сохраняйте действующие `/private/contact/config.php` и `runtime/`. Они не входят в архив. Не переписывайте `.htaccess`, `.user.ini` или PHP-обработчик при обновлении только HTML/CSS, если их изменение не требуется.
4. Загружайте новые файлы в промежуточную папку вне document root, проверьте размеры/контрольные суммы и права. Для FTPS проверяйте сертификат; не отключайте TLS-проверку. Приватные файлы никогда не размещайте в публичной папке даже временно.
5. Замените проверенные файлы. Для ограниченного обновления допустимо переименование отдельных файлов; это не атомарная замена всего сайта. Ресурсы размещайте до HTML, robots/sitemap — после. При удалении маршрутов отдельно проверьте удаление старых публичных файлов и нужные перенаправления.
6. При ошибке остановитесь и восстановите затронутые файлы из резервной копии. Не продолжайте загрузку поверх непонятного состояния.
7. Проверьте по публичному HTTPS-адресу главную, изменённые страницы, форму, ресурсы, canonical, robots и sitemap; HTTP/www должны сохранять путь и query при переходе на основной домен. Несуществующий путь и приватная конфигурация должны быть недоступны (404).
8. GET токена формы проверяет доступность обработчика, но не доставку письма. Локальные тесты не должны отправлять реальные письма. Полную проверку доставки проводите в рамках согласованной тестовой отправки и подтверждения получателем; не подменяйте это выводом об успехе по HTTP.
9. Запишите дату, commit, состав обновления, резервную копию и фактически выполненные проверки в `docs/deployment.md`. Не включайте туда пароли, токены, ключи или содержимое заявок.

## Секреты и инфраструктура

- Конфигурация SMTP и техническое состояние — только на сервере вне публичного корня. Для примера используется `config.example.php` с безопасными значениями, рабочий файл не коммитится.
- Не выводите секреты командами диагностики, не передавайте их в URL или аргументах процессов, не сохраняйте в GitHub/CI без явной задачи на такое хранение.
- Не меняйте DNS/MX, почтовую маршрутизацию, TLS, права доступа и инфраструктуру попутно с обновлением сайта. Проверки не должны ослаблять защиту.
- PHPMailer хранится вместе с лицензией и `SOURCE.json`. Обновление зависимости требует проверки происхождения и теста SMTP; не редактируйте vendor для случайного обхода ошибки.
- Настройка планировщика очистки и юридические данные компании — отдельные эксплуатационные задачи. Наличие инструкции не означает, что они выполнены.
